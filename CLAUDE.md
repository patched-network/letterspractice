# LetterPeople: Interactive Character System

**LetterPeople** are the core of the application - animated letter characters with faces, arms, and expressive capabilities. They serve multiple roles:

1. **Instruction delivery**: Characters "speak" phonemes, demonstrate letter shapes, and guide learning through animations and expressions. They narrate the exposition and introduction of new concepts.
2. **Primary UX**: The letters themselves ARE the interface - learners interact directly with characters rather than abstract buttons or text
3. **Exemplifying learning process**: The letters practice. As in - they persue skill development in their interests, modelling both effective learning strategies, and a nurturing relationship between the upper and lower cased letters.

## Capabilities

- **Facial expressions**: Eyes (with tracking, blinking, looking), eyebrows, mouth shapes for emotions
- **Body language**: Arms for waving, gesturing, pointing; full-body 3D rotation; locomotion (walking, jumping)
- **Advanced choreography**: Scene staging with depth, speech balloons, juggling animations
- **Transforms**: Geometric arrangements (fan, scatter, rainbow), procedural animations

## Implementation

Built as a TypeScript library (`src/letterpeople/`) rendering SVG with anime.js animations:
- Letter renderers for A-Z, a-z, punctuation
- Attachment system (eyes, mouth, arms, body controller)
- Vue integration via `WordDisplay` component
- OKLCH-based color system for perceptually uniform adjustments

## Usage

See `src/letterpeople/CLAUDE.md` for comprehensive documentation including:
- Three levels of API abstraction (LetterInstance, Word class, Vue components)
- Animation patterns and attachment controllers
- Transform system and scene staging
- Juggling and locomotion systems

**Quick example:**
```typescript
const letter = createLetter('A', container, { showEyes: true, showArms: true });
await letter.eyes.show({ duration: 300 });
await letter.arms.wave({ duration: 600 });
```

# Phonetics Service

**Strongly-typed phonetics system** providing ARPAbet phonemes, grapheme-phoneme correspondences (GPCs), and phoneme audio for words with recorded audio.

**See `src/services/phonetics/CLAUDE.md`** for comprehensive documentation including:
- ARPAbet type system and utilities
- Phoneme audio caching (staggered prefetch)
- Phonetic index API and data structures
- Build process (CMUdict → generated index)
- Integration with PhoneticWord component
- Future expansion (full GPC rules, decoding algorithms, phonological awareness)

**Quick example**:
```typescript
import { getPhonetics, getPhonemeAudioUrl } from '@/services/phonetics';

const phonetics = getPhonetics("ship");
// => { phonemes: ["SH", "IH", "P"], chunks: [...], audioUrl: "..." }

const url = getPhonemeAudioUrl("SH"); // => "/audio/phonemes/sh.mp3"
```

**See `content/phoneticAnalytics/CLAUDE.md`** for the pipeline map, build

Key things to know app-side:
- **Curriculum single source of truth:** `content/phoneticAnalytics/lib/curriculum.ts`
  (lesson registry, per-GPC lesson assignment, concept tags, threshold
  policies). App imports it via the `src/services/curriculum.ts` façade;
  `src/services/lessons.ts` derives lesson gating/availability from it, and
  `src/services/LessonGateFilter.ts` enforces **default-deny** gating.
- **Generated state-of-the-world:** `content/phoneticAnalytics/outputs-v2/curriculum-coverage.md`
  — every GPC × curriculum state × card counts (versioned; re-tag diffs show
  blast radius).
- **Live admin view:** `/admin/content` → **Lessons** tab
  (`src/views/admin/AdminContentView.vue`) renders the curriculum consistency
  checklist + unassigned/deferred pools against the live DB.

# Public pages: search, link previews, AI crawlers

The app renders in the browser, so without help every route's HTML is the same
empty shell. Crawlers that don't run JavaScript (most AI crawlers, every
link-preview bot) would see only the site-wide title. So:

- **`src/content/pages.ts` is the list of public pages**: route name, path,
  aliases, title, description. `services/pageMeta.ts` applies each one's head
  on navigation, and **every route not listed there is marked `noindex`**. A new
  marketing or content page must be added to `pages.ts`, or it won't be indexed.
  `pages.test.ts` checks the list against the router.
  A deployment's own public pages (ours: Privacy, Terms) come from its overlay's
  `pages.ts` (`src/deployment/index.ts`); `pageMeta.ts` and the prerender append them.
- **`build:webapp` prerenders them** (`scripts/prerender-public.ts`): each public
  page and changelog entry becomes `dist/_prerendered/<path>.html`, with its own
  head and a static copy of the content, which browsers running JS don't show,
  except a part marked `data-prerender-show` (the landing page's hero): that
  shows from the HTML until Vue mounts, so the first paint doesn't wait for the
  bundle. Keep such a part's layout CSS-driven; anything sized by script needs
  `data-prerender-blank` and CSS that reserves its space (see
  `HeroReadVignette.vue`). Check the hand-over after touching the hero or the
  app shell: `npx tsx scripts/perf/hero-swap-check.ts <local build URL>
  --engine chromium|firefox [--viewport desktop]` (fails on any move, blink or
  late font). On such a page the app's script starts only after the first
  paint (`scripts/vite-plugin-boot-after-paint.ts` replaces the entry's
  `<script>` tag; check with `scripts/perf/paint-before-boot.ts`). The build also writes `sitemap.xml`, `changelog.xml`
  (Atom), `llms.txt` and the robots.txt `Sitemap:` line, then a brotli `.br` beside each
  compressible file (`scripts/precompress-dist.ts`; served with Caddy's
  `precompressed br`). It fails if a page renders blank, a deferred section is
  still loading, or its runtime head disagrees with the static one. Needs `VITE_SITE_URL` (the deploy supplies it) and a
  Playwright Chromium; `SKIP_PRERENDER=1` skips the browser step. A
  deployment's robots.txt policy (extra sitemaps, a Content-Signal line) comes
  from `ROBOTS_*` env, not this repo; see the script header.
- **Preview images**: every page names one (`og:image`, with size and alt
  text where there is one); `SITE_IMAGE` unless the page has its own.
  `pages.test.ts` fails while a named image is missing or the wrong size.
- **Drawn preview cards** (1200×630, committed PNGs under `public/`), all in
  one frame (`components/og/OgCardFrame.vue`): each live lesson's
  (`LessonOgCard.vue`), and the page cards in `PAGE_OG_CARDS`
  (`curriculum/ogCard.ts`): the site-wide default `/og-image.png`
  (`SiteOgCard.vue`, a draft: the live PNG is hand-made, and the draft exports to
  `tmp/og-drafts/`), /exercises, /curriculum, /learning-engine and the
  fridge sheet. `/dbg/og` lists every route's preview image and draws the
  cards live; export with `npx tsx scripts/export-og-cards.ts [ids…]` (dev
  server up; ids are lesson ids or page-card ids). Re-export and commit after
  a card's look or copy changes, or what it draws does (a lesson's still or
  facts, `FridgeSheetMini`, the exercise views); `ogCard.test.ts` fails while
  a live lesson has no card.
- **Lesson previews** (`/curriculum/lesson/<id>`, `LESSON_PAGES` in `pages.ts`)
  are for sharing, not search: own title, description and preview card, but
  `noindex` and out of the sitemap. The prerender writes them head-only, at the
  lesson's path and at each `/c/l/` short link (the router's redirect runs in
  the browser, which preview bots don't).
- Serving the prerendered files is a server rewrite (the deployment's web
  server); the script header has it.

# Keyboard Context System

The application uses a **Keyboard Context** system as a mainline input mechanism, especially for the primary learning loop.

## Purpose

- **Scaffolded guidance**: Dynamically constrains which keys are active/enabled, guiding learners toward valid responses
- **Incremental hints**: Provides visual feedback (highlights, colors, animations) to scaffold difficulty
- **Unified input**: Single keyboard component serves multiple question types and learning activities
- **Accessibility**: Large, phoneme-aware keys suitable for early learners and touch devices

## Architecture

The system uses Vue's provide/inject pattern:

1. **Provider** (e.g., `StudyView.vue`): Creates context, owns the `ProgressiveKeyboard` component, dispatches events
2. **Consumers** (question components): Inject context, configure which keys to show/enable, respond to key events

## Key Files

- **Composable**: `src/composables/useKeyboardContext.ts` - context creation, injection, event subscription
- **Types**: `src/composables/keyboardContext.types.ts` - TypeScript interfaces
- **Keyboard UI**: `src/components/keyboard/ProgressiveKeyboard.vue` - the visual keyboard component

## Usage Patterns

```typescript
// In a question component (consumer):
const keyboard = useKeyboardContext();

// Configure what keys to show
keyboard.requestConfig({
    letters: ['c', 'a', 't'],
    enabledLetters: ['c'],  // only 'c' is pressable initially
    showAdvance: true,
    advanceColor: '#FF5722',
});

// Listen for input
keyboard.onKeyTap((event) => handleInput(event.letter));
keyboard.onAdvance(() => handleSpacebar());

// Clean up on unmount
onUnmounted(() => keyboard.clearQuestionConfig());
```

Components can also accept `keyboardContext` as an optional prop (see `PhoneticWord.vue`) to work both inside and outside keyboard-providing contexts.

## Debug Views

- `/dbg/kbc` - Keyboard Container layout with persistent keyboard for testing child components
- `/dbg/kbc/phonetic` - PhoneticWord with spacebar-driven stepping
- `/dbg/keyboard-context` - Full context API testing with SpellingQuestion

# Local Development with CouchDB

For iterating on DB-backed features (card rendering, study sessions, navigation strategies) without deploying to production.

**Without a CouchDB URL configured, the app runs on the static course** (`public/static-courses/`, guest-only, progress in the browser; selection logic in `src/ENVIRONMENT_VARS.ts`). Setting `VITE_COUCH_BASE_URL` in `.env.development`, as below, selects CouchDB. After a curriculum change, `yarn pack:course` (docker) regenerates the static course; CI fails while the committed copy is stale. In the dev console, `__lp.docs('<id prefix>')` lists the local learner's docs.

## Prerequisites

- **Docker** installed and running
- **A vue-skuilder checkout** (for its `test-couch` docker setup)
- **Generated card data** in `content/phoneticAnalytics/outputs-v2/` (run `yarn gen:all` from that directory if missing)

## Quick Start

```bash
# Terminal 1 — Start local CouchDB (one-time, or after reboot):
cd <vue-skuilder checkout> && yarn couchdb:start

# Terminal 2 — Seed the database with cards + strategies:
cd content/phoneticAnalytics
yarn db:seed

# Terminal 3 — Run the app against local CouchDB (from the app root):
yarn dev
```

Or, as a single command that seeds then starts vite:

```bash
yarn dev:local
```

Log in as `test`/`test` (from the framework's test-couch docker snapshot). The app auto-registers the user for the course on login.

## How It Works

| Component | Details |
|---|---|
| **CouchDB** | Docker container via `vue-skuilder/test-couch/test-couch.sh` (CouchDB 2.3.1, `admin`/`password`, port 5984) |
| **Seed script** | `content/phoneticAnalytics/scripts/seed-local-db.ts` — wipes and recreates course DB, inserts design docs + lookup entry, then runs `deploy-content` |
| **Env config** | `.env.development` sets `VITE_COUCH_BASE_URL=localhost:5984/` so PouchDB connects to local couch |
| **Vite proxy** | `vite.config.ts` proxies `/couch` → `localhost:5984` (for any fetch-based requests) |

## Key Scripts

- `yarn db:seed` (from `content/phoneticAnalytics`) — bootstrap + upload cards to local CouchDB
- `yarn db:seed --skip-upload` — bootstrap DB structure only (design docs, lookup), skip card upload
- `yarn dev:local` (from the app root) — seed + start vite in one command
- `yarn deploy:content --url http://localhost:5984 -u admin -p password` — deploy cards only (assumes DB already exists)

## Environment Files

- `.env.development.example` — tracked template; copy to `.env.development` for local dev
- `.env.development` — gitignored; consumed by Vite to set CouchDB connection URL

## Design Documents

The seed script inserts CouchDB design documents (`_design/elo`, `_design/getTags`, `_design/cardsByInexperience`, `_design/_auth`) whose canonical definitions live in `@vue-skuilder/express/src/design-docs.ts` and its `assets/` directory. The seed script reads the asset files directly where possible and falls back to inline definitions.
